审查日期：2026-10-26（Asia/Shanghai）。对象：当前源码、0.4.0-rc.2 候选包及其默认/实验配置。对照文件：2026-10-25《架构技术审查报告.md》。独立完成本次审查，没有调用子代理，没有生成 HTML，没有修改生产实现、正式知识库或发布索引。

**结论：按原报告末尾的 6 组整改事项统计，1 组完整解决，3 组部分解决，2 组仍未解决。不能判定整个架构已闭环。当前仍适合“静态、只读、本地、可追溯证据检索”的定位；不能据此签署动态更新、任意中断自恢复和完整排名重放的验收通过。**

这里的“部分解决”包括两种明确情形：只在显式启用的实验配置中修复，或者机制已实现但原问题要求的整体能力仍有缺口。二跳保底、二跳专项提升指标和学生出题是用户主动取消的设计与流程，不计为待补的缺陷，也不冒充已经通过的验收。

本次确认当前 13 个 src 文件与已验证的 rc.2 一致，正式知识库哈希也一致。旧 0.3.0 包未被覆盖；下列源码修复不会自动出现在仍使用旧包的客户端里。

## 2. 仍需优先处理的实质问题

### [P1] WAL 逻辑快照仍可绕过一致性检查

在隔离副本中，先建立正常的 WAL 基线并绑定匹配索引，再在同一图谱版本下同时修改命题、原文和引文。更新均已提交，但尚未 checkpoint。

本次结果：主 graph.sqlite 哈希不变；WAL 有 12,392 字节；向量文件未变。旧会话返回缓存旧文本，新会话返回新文本并继续启用 semantic_vector，两个会话均 degraded=false，新会话 index_problem=null。这不是仅凭代码推测，也没有利用损坏引用制造假例子。

根因仍是 [fingerprint](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:68) 主要绑定主文件及普通文件属性，没有绑定 SQLite 的逻辑快照。调用方“只读打开”不等于其他进程不能写入。

**风险范围：** 需要可写数据库、同版本提交且未 checkpoint 这一条件。不能将它描述为现有静态交付包已经损坏；但只读快照合同目前还依赖操作约定，未形成硬约束。

终审要求：若继续采用静态交付，优先形成可验证的不可变快照准入；若以后支持在线写入，则索引必须绑定实际一致快照，不能仅绑定主文件字节。

原有“完整检查点后被终止可以继续”只是其中一个成功情形，不能推出所有中断都可恢复。当前错误仍被限制在构建目录，旧发布快照没有因此被破坏；问题是恢复合同不完整。

### [P2] 默认行为和实验能力必须分开验收

[默认 profile](C:/Users/13240/Desktop/RAG/chan-kg-agent/profiles/default.json:4) 仍是 hybrid-graph-rerank。[GraphStage](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/graph-stage.mjs:10) 仅对 hybrid-graph-v2-rerank 使用新遍历；新准入也仅在这个配置中启用。因此默认请求仍有原 RRF 截断、宽触发及缺少细粒度节点/扇出限制的问题。

本次实际询问“如何烤披萨？”：默认配置仍扩展 20 条支持路径；新配置以 no_query_anchor 跳过 Graph。但**两种配置的检索状态仍都是 found**，因为文本检索依然会给出缠论候选。Graph 门控解决的是“是否扩图”，不是整个检索器的领域外拒答能力。

默认不开启实验策略有合理依据：质量优势没有得到证明。这里不建议为了销项直接切换默认，而要求后续发布说明和验收统计继续明确区分两条路径。

### [P2] 可信度及重放能力仍有原缺口

- [eligible](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:103) 仍按复核状态及文档/概念过滤，没有验证当前问题满足命题条件。引用有效不等于该关系适用于当前问题。
- [定义锚点](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:334) 在重排后仍被放到前面。这是保留的业务优先规则，错误的定义关系仍可能被放大；取消二跳特殊待遇没有取消定义锚点。
- [fusion](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/lexical.mjs:41) 重写 reasons 时仍只保留 channel/rank/score，没有保留 [dense 返回](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/dense.mjs:33) 的窗口位置和模型 revision。
- 包内已有版本字符串、请求 profile 和预算摘要，但仍没有足以单包重放的有效请求与完整代码、模型、配置、索引内容指纹。外部评测回执有哈希，不等于每个查询包都可重放。
- 正式库与原审查的数据库哈希一致，概念类型、别名覆盖、改名 ID 迁移、边条件/歧义和 requires 环的治理没有发生。不能将未修改的本体称为已经治理。

这些缺口不要求引入分布式图数据库，也不要求随意补一列“置信度=0.9”。应先明确规则的适用条件与可审计状态。

## 5. 按 architecture skill 审视 module 深度

仓库未发现适用于本范围的 GLOSSARY.md 或 docs/adr 记录；沿用现有“命题、原文、证据、概念、关系、问题组”的语言。以下是审查判断，不是本次实施重构。

**值得保留的深 module。** 三个调用入口共用 RetrievalService 的 interface，CLI 与 MCP 是真实 adapter，调用方 JavaScript 也走同一逻辑。按 deletion test，删除该 module 会把知识状态、证据封装和错误规则扩散到多个入口；目前具有实际 depth、leverage 和 locality。没有理由再拆成一批只转发的小 module。

**Strong：快照与发布 module。** 当前运行期身份检查、索引构建、向量检查点和发布文件写入分别管理同一个“可用快照”事实，缺少集中验证。下一轮最值得提高 depth 的是这一 module：在明确的 seam 后集中恢复与发布不变量，通过同一 interface 用真实 SQLite/文件 adapter 验证中断、重试、更新和删除。其 leverage 是构建与运行共同遵守同一份身份合同，locality 是存储错误及验收不再散落。这里不预设未来远程数据库 adapter，也不提出新的 interface 形状。

**Worth exploring：Graph 执行状态的 locality。** GraphStage 已收纳遍历与验证，但父 module 仍直接清理 view、覆盖 paths/anchors、补算旧策略缺失分数、在包装错误时再次回退。这表明成功提交和撤销尚未完全集中。应在修复真实缺口时收拢这些状态所有权，通过现有 interface 验证，而不是立即增加通用策略框架；不为二跳新增 seam 或 adapter。这样增加 depth 与 leverage，不扩大外部调用负担。

**暂不建议的工作。** 为当前规模换 ANN、分布式图库、并行 worker，或为二跳增加专用通道，都缺少当前证据支持。性能主要仍由重排决定；本轮优先级应是快照正确性与失败恢复。
