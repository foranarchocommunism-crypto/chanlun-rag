# 缠论 Agent 0.3.0 架构技术审查

审查日期：2026-10-25（Asia/Shanghai）。对象：当前 `chan-kg-agent`、canonical SQLite、当前派生索引，以及 0.3.0 Windows x64 交付目录。审查方式：实现检查、全量结构核验、真实本地模型查询、开发排名回放、隔离副本和合成夹具故障注入。未修改生产代码、正式知识库或发布索引。

**结论：当前方案具备可用的静态、本地、可追溯证据检索基础；Graph 的新增召回、多跳有效性、图通道容错和构建恢复尚不足以支持“成熟的动态多跳 GraphRAG”验收。** 证据保存和默认 reviewed 隔离是优势。普通图扩展主要调整已有文本候选的顺序，定义锚点则确实能直接改变最终结果。

审查发现来自当前实现与本次复现，不把历史交付成功当作架构能力证明。源码中的 10 个关键模块与正式目录逐文件哈希一致；canonical DB/manifest、索引 manifest/projection/vector、profile 和 policy 的 7 组文件也与正式目录一致。本报告的主要检索发现适用于该交付目录。比较结果见 [源码与运行证据](C:/Users/13240/Desktop/RAG/validation-runs/architecture-review-20261025/runtime-audit.json) 和 [数据比较](C:/Users/13240/Desktop/RAG/validation-runs/architecture-review-20261025/data-delivery-comparison.json)。

**实际执行链路。** 普通 knowledge 请求先执行结构化词法，再执行本地向量召回；两路加权 RRF 融合后，取前 5 条命题关联的概念作为图种子。图扩展读取关系的支持命题，经过第二次 RRF 截取前 100；定义意图还会将至多 2 个定义锚点前置。随后重排前 40 个候选，再次将定义锚点置顶，最后补取已知问题组并按完整证据单元封装。词法与向量是两个召回通道，当前代码执行是顺序的。参见 [检索主流程](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:210)。

**1. Graph 建模、抽取准确性和独特价值。** 当前库有 318 个概念、692 条关系、6,008 条命题，其中 reviewed 3,369、pending 2,611、rejected 28。reviewed 中 3,366 条 explicit、3 条 inferred，473 条保留显式歧义。对应的 reviewed 引文证据为 4,584 条。整个 evidence 表共有 7,225 条，不能把它们都称为 reviewed。

命题与原文之间有独立 evidence，证据保存码点区间、实际 PDF 页、来源身份和几何位置；命题保留 conditions、exceptions、kind 和 review_note。这种结构适合提供可供 Agent 复核的证据。当前结构与引用检查没有发现断链、引文偏移不匹配或 reviewed 引用身份违规，现有 canonical validator 也通过。

不过，**引用精确不等于命题蕴含正确，更不等于边的方向和类型正确**。3,459 条 review 记录的 reviewer 名称均为 Agent/模型或主代理描述，没有独立人工金标准的当前证据。已有 240 题开发集和 24 题前瞻集评估的是标注证据召回，不能当作抽取准确率或最终答案正确率。本次按 7 种关系类型抽出 20 条关系及支持原文，保存在 [关系样本](C:/Users/13240/Desktop/RAG/validation-runs/architecture-review-20261025/relation-samples.json)；没有据小样本编造 precision/recall。

Graph 的价值需分开评价。普通局部扩展、定义锚点、歧义问题组是不同机制。已知问题组由 policy 的 claim ID 触发，词法模式也会补取，因此这部分收益不能全部归给图遍历。真实查询“中枢是什么，成立需要什么条件？”在启用 Graph 定义锚点时把 `upper-l017-center-definition` 放在第 1；关闭图预算和深度后，即使保留同样的重排器，它不在前 3。这证明定义锚点确实影响结果。

**2. 普通图扩展的新候选被融合公式排除，属于优先修复项。** 当前词法、向量、Graph 权重分别为 1、0.5、0.1，RRF 常数为 60。只由 Graph 命中的候选，其最好分数为 `0.1/(60+1)=0.001639`；词法第 100 名已有 `1/(60+100)=0.00625`。只要词法召回满 100 个，普通 Graph 新候选不可能进入第二次融合的前 100，因而也没有机会进入前 40 重排。这里不包括另有强制前置逻辑的定义锚点。

本次用当前 graph/fusion 代码回放已记录的 240 题原始词法/向量排名，236 题存在文本两路都未命中的图支持候选，共计 2,454 次候选出现；进入融合前 100 的次数为 **0**。这是跨问题累计出现次数，不是 2,454 个不同实体。`additional_candidates` 只是相对于种子排名前 limit 的差集，不能解读成相对于两路候选池的净新增。参见 [决策回放](C:/Users/13240/Desktop/RAG/validation-runs/architecture-review-20261025/graph-decision-audit.json)、[二次融合截断](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:259) 和 [RRF 公式](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/lexical.mjs:41)。

隔离普通图扩展、排除定义锚点和重排后，证据 Recall@20 从 88.2361% 变为 88.4444%，增加约 **0.2083 个百分点**；完整证据组从 80.4167% 变为 80.8333%，240 题中 1 题改善、0 题下降。该结果复现了已有消融记录。它说明当前图通道有有限排序价值，不能把整个系统相对词法的提升归因于 Graph。本次没有重新运行 240 题全部 embedding/重排，也没有重新调参或重新使用前瞻集调优。

建议在重排前为确有支持的 Graph 新候选设置小规模、独立的准入名额，并同时保留总候选上限；用独立关系/多跳题验证新增收益。不要只提高 Graph 权重：现有开发记录中权重提高至 0.25 时出现了 3 题退化。

**3. Graph 错误会怎样放大。** reviewed 及证据存在性是硬过滤；图路径保留原方向，反向探索标为 association，路径语义明确为“有证据的关联，不是传递推论”。这些设计减少了错误被直接升级为逻辑结论的风险。

风险仍在：reviewed 并不保证语义正确；一条错误但有引用的关系能够加分，定义类关系甚至能触发最终置顶。扩展没有验证当前问题是否满足支持命题的适用条件，没有按歧义、证据独立性或关系可信度降权。定义锚点经过重排后仍被重新放到首部，所以它绕过了重排器的最终排序决定。这个优先规则可以有业务价值，但其错误传播风险应单独测试。[路径过滤](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/graph-expansion.mjs:19)、[最终定义置顶](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:285)。

关系没有数值 confidence；importance 是整理重要性，不能充当可信度。建议先建立可解释的边级复核/歧义/适用条件状态，并做独立语义抽查与错误边注入验收。若以后采用概率置信度，应校准后使用，不应随意给 reviewed 边统一填写一个高概率。

**4. Graph 如何触发、遍历、排序和回退。** 主路径先取得词法和向量候选，再从前 5 条命题取得概念扩展，属于文本候选驱动。问题直接提及概念或别名会提高相关关系的遍历优先级，通常不独立生成图种子。定义锚点是额外的实体入口：匹配“什么是 X / X 是什么 / X 定义”等句式，再检查出向的 reviewed `defines/requires/composed_of` 关系和 explicit 命题主谓结构。

默认 profile 为 `hybrid-graph-rerank`，knowledge/research 的非零图预算会触发扩展。没有关系问句分类器、低置信召回门控或领域外拒绝机制。真实测试“如何烤披萨？”也运行了图扩展，产生 20 条支持路径并返回 `found`；返回包同时注明 `answer_support=not_assessed_by_retrieval`。这不是证明系统回答了烹饪问题，而是表明 Graph 触发和证据适用性筛选过宽。source 模式不实际扩图，但 runtime 的 actual_channels 仍会列出图通道，说明通道标记还需改进。

| 控制项 | 当前实现与判断 |
| --- | --- |
| 图深度 | 默认 1，API 最大 2；有显式上限 |
| 图路径预算 | 默认 20，最大 100；按支持命题路径计数，重复边的不同支持会分别消耗预算 |
| 种子 | 固定前 5 条命题；240 题回放实际带入 5–21 个概念，平均约 12.49 |
| 节点总数 | 没有独立 request 预算；不能将路径上限直接称为节点上限 |
| 单节点扇出 | 没有独立配额；所有关系统一按 query 提及、种子支持排名及 relation ID 排序 |
| 类型与方向 | 普通扩展没有关系类型白名单；允许入边关联探索并明确记录方向；不做传递推断 |
| 候选及重排 | candidateBudget 默认 100、最大 1,000；rerankBudget 只允许 20 或 40 |
| 上下文 | 按 JSON 数据对象的 Unicode 码点预算封装，不是 tokenizer token 数 |

本次把 `graphDepth=2`、`graphBudget=20` 用于 240 题回放，全部第一跳就用满预算，二跳路径为 0；放宽到允许的 100 条后，也只有 22/240 题产生二跳路径。程序具备两跳路径枚举能力，但默认预算下没有证明有效的多跳召回，更没有问题分解、关系约束求解或多跳答案正确性的验收。相关记录见 [运行审查](C:/Users/13240/Desktop/RAG/validation-runs/architecture-review-20261025/runtime-audit.json)。

普通图路径排序没有路径长度惩罚、边置信度乘积或类型权重，图通道通过 `0.1/(60+rank)` 参与 RRF；定义锚点采用强优先。其语义是相关性，不是真实性概率。

**Graph 通道容错未通过。** 在不破坏 canonical 证据、词法或向量的情况下，给关系遍历注入异常；`hybrid-graph + allowDegraded=true` 仍抛出 `AUDIT_GRAPH_FAILURE`。同一服务改用 `hybrid` 即可正常返回。原因是图扩展与定义锚点不在错误隔离块内，而 dense/rerank 有相应处理。[故障位置](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:241)。应在明确允许降级时隔离图通道，返回真实降级原因；若 canonical 原文或其身份完整性已损坏，仍应拒绝返回，不能盲目降级。

**5. Vector 与 Graph 一致性实测。** 生产运行采用不可变整套快照，而非在线双写。启动时比对 DB、manifest、policy、projection、模型和 profile，普通查询还检查文件指纹。这个方式适合固定语料；更新和删除须发布匹配的新知识/索引并重新打开服务。本次在隔离合成数据上调用未修改的真实构建脚本和本地 ONNX 模型，结果如下。

| 场景 | 实际结果 | 评价 |
| --- | --- | --- |
| 修改命题和原文，继续使用旧索引 | 默认 INDEX_STALE；显式降级用当前文本词法返回 | 防陈旧索引有效 |
| 更新后构建新索引和向量 | 新文本正常返回，该命题向量字节改变 | 通过 |
| 删除命题、证据及相关边后用旧索引 | INDEX_STALE | 通过 |
| 删除后整套重建 | 旧 claim 查询 UNKNOWN_ID，vector rows 不再有该 claim | 通过；此场景是命题删除，不是删除整份来源 PDF |
| rollback-journal 模式直接修改服务正在使用的 DB | 现有和新会话都拒绝陈旧索引 | 通过 |

另有一个**可写数据库边界问题**。隔离副本启用 WAL、在建立有效基线后提交同版本的 claim 更新且暂不 checkpoint：主 `graph.sqlite` 哈希不变。现有会话返回缓存旧文本；新会话返回新文本但继续使用旧向量，两者均 `degraded=false`。checkpoint 后才被识别为 INDEX_STALE。原因是指纹和哈希主要覆盖主文件，不覆盖 WAL 里的逻辑数据库快照。[指纹及校验](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:65)。该条件不等同于当前不可变发布包已经损坏；它说明现有保证不能外推为“任意在线写入都能保持一致”。若保留静态交付定位，应显式拒绝活动可写/WAL 状态，或先取得 SQLite 一致快照再索引和发布；不要只增加一个增量接口便宣称一致性完成。

**6. 本体与图结构的具体检查。** Document、Passage、Claim、Evidence、Concept 等身份由不同表区分，基础分层清楚。但 `concepts` 没有领域 `entity_type`，318 条 description 全为空；术语、级别、形态、指标、操作、定理等角色混在一个类型中。不能依靠节点类型约束关系的 domain/range。[数据合同](C:/Users/13240/Desktop/RAG/chan-kg-agent/contracts/schema.sql:11)。

只有 6 个概念登记了别名，共 7 个别名；NFKC、大小写和去首尾空白后的名称没有跨 ID 冲突。导入器会合并已登记的 exact label/alias，但没有语义同义实体发现及规范化合并机制。318 个 concept ID 均为 label 的哈希；同样的规范名称会稳定复现，改名后重新导入则可能产生新 ID。应保留原 ID，建立经审校的别名、改名和合并迁移记录。

边有 source、target、type、支持 claim IDs 和 review_status，可从 claim 继续追到 evidence 和原文。缺少独立的有效时间、边级置信度、边级条件和边级歧义。原文 published_at 和命题 review.checked_at 能追溯来源时间，不能替代关系 valid_from/valid_to。当前固定历史语料不一定需要引入完整时态图，但接口必须区分这两种时间。

7 种关系中 qualifies 为 380/692，related 为 128/692，合计约 73.4%。这不证明它们错误，但显示主要用途是宽泛的限定与关联导航。无关系类型消融，不能认定每类都有独特检索收益。当前机器可证明所有关系支持引用有效，不能证明 qualifies 的具体语义一致。

无自环、重复三元组、悬空端点或缺失支持；65 个概念没有任何 relation。最大度数节点为“走势中枢”51、“操作级别”47、“背驰”39；这是相对枢纽，尚无超大规模节点证据。混合关系图存在大小为 97 和 2 的强连通分量；单看 requires 还存在“走势类型/走势中枢”二节点环及“背驰段/区间套/确认”三节点环。composed_of 和 defines 子图没有发现同类型有向环。上述 requires 环可能涉及不同条件或定义层次，需要逐边语义复核，不能仅凭有环就判为知识错误，也不能把它直接当作无条件依赖 DAG。当前 visitedRelations、两跳上限和路径预算避免了无限遍历。全部结构证据在 [graph-structure.json](C:/Users/13240/Desktop/RAG/validation-runs/architecture-review-20261025/graph-structure.json)。

**7. 多阶段效率与复杂度。** 当前向量为 15,520 个唯一 512 维向量、23,088 条检索窗口映射；DenseIndex 逐行过滤并计算相似度，没有 ANN。Graph 每次对全部 692 条关系排序及扫描，没有使用邻接索引；已构建的 claim_concept、relation_support 投影也未用于当前图遍历。词法索引在服务内首次按模式建立并缓存。对于现在的数据量，这些方案仍能工作，不应仅为了架构名词就引入分布式图数据库或向量服务。

本次 6 次顺序热查询耗时约 0.985–1.199 秒，六个观测值的中位数约 1.152 秒；词法约 1–3 ms、向量约 20–26 ms、图约 3–4 ms，重排约 0.94–1.15 秒，重排是主要瓶颈。该小样本不作为生产 p95。服务构造约 0.77 秒，运行进程观测峰值约 1.24 GiB；资源测量来自本次机器，不能当作其他硬件的承诺。

4 个同时提交的请求按队列串行执行，第 4 个调用端等待约 4.67 秒，而包内 `runtime.elapsed_ms` 只报告其开始执行后的约 1.23 秒，遗漏约 3.44 秒排队时间。应记录 enqueue/start/end 并设置队列/超时预算，再按实际并发目标决定是否增加 worker。优先评估按意图选择是否重排、已知 ID 走直接查证接口；图扫描只有几毫秒，不是当前首要性能瓶颈。[串行队列](C:/Users/13240/Desktop/RAG/chan-kg-agent/src/retrieval.mjs:205)。
